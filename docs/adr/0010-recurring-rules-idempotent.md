# 10. Recurring generation is idempotent per occurrence

- **Status**: Accepted
- **Date**: 2026-10-27

## Context

A daily job that can be retried, overlapped or interrupted must not double-charge
a user, and a rule anchored to the 31st must not permanently drift to the 28th
after February.

## Decision

- `recurring_rules.next_run_on` is the authoritative cursor. It advances only
  over occurrences that were emitted (or found already present).
- Transactions generated by a rule carry `(recurring_rule_id, occurrence_on)`,
  protected by a partial unique index, so a retry converges.
- Monthly/yearly advances use the rule's intended day-of-month and month anchor,
  clamped to the target month's length. A long catch-up is capped per run
  (500 occurrences); the cursor resumes on the next run.
- `ends_on` is inclusive of the final occurrence. The job skips rules locked by
  another worker (`FOR UPDATE SKIP LOCKED`).

## Consequences

- The API can expose a manual `POST /recurring-rules/{id}/run` safely.
- Deleting a generated transaction does not cause it to be regenerated; the
  rule has already moved past that occurrence.
